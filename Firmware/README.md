# Changes vs. the public firmware

**Current version: v1.0.3.** The public v1.0.0 baseline this README diffs
against (previously at the now-retired `Pwnsat/FlatSat_Firmware` repo,
commit `f94aa87`, "FlatSat Firmware v1.0.0 Public") is preserved as a
[legacy v1.0.0 release](https://github.com/Pwnsat/FlatSat/releases/tag/v1.0.0)
on this repo — binary only, since merging its source files alongside this
folder's would just create two conflicting copies of the same file names.

This README documents everything v1.0.3 adds or changes relative to that
v1.0.0 baseline, generated by a direct file-by-file `diff` between both
source trees, not from memory.

## Changelog highlights (v1.0.0 → v1.0.3)

* **New:** ground-station authentication, mission modes, downlink
  encryption (AES-128), GPS navigation, a simulated SpaceCAN bus console,
  a "secured" SPP packet variant, 4 new APIDs — see **New features**
  below for the full breakdown.
* **Fixed:** LoRa radios failing to initialize (missing `tcxoVoltage=0.0`),
  a downlink transmit race, debug-mode payload corruption, 32 misaligned
  serial log lines — see **Bugs fixed** below.
* Every new subsystem above ships with at least one intentional
  vulnerability, backing the [8 attack scripts](../Attacks/) and the
  wiki's [Attack Walkthroughs](https://github.com/Pwnsat/FlatSat/wiki/Attack-Walkthroughs-00-07).

## Summary

The public firmware is a functional baseline: two SX1262 LoRa radios,
CCSDS/SPP protocol, sensors (IMU, BME280), dual-core USB serial console.
This firmware builds on that base and adds **a full layer of simulated
real-satellite-mission subsystems** (ground-station authentication, mission
modes, downlink encryption, a simulated CAN bus, GPS navigation) — with
intentional vulnerabilities, which are what the attack scripts under
[`../Attacks/`](../Attacks/) exploit.

## How to build

**Board:** Raspberry Pi Pico / RP2040 (`#include "hardware/watchdog.h"` is a
Pico SDK header; the sketch uses the RP2040 core from
[earlephilhower](https://github.com/earlephilhower/arduino-pico), which
ships native USB support via `Adafruit_TinyUSB` for this firmware's dual-USB
core).

**Third-party libraries** (Arduino Library Manager, or the PlatformIO
equivalent):

| Library | Used for |
|---|---|
| `RadioLib` | SX1262 LoRa radios (uplink/downlink) |
| `Adafruit_BME280` (pulls in `Adafruit_Sensor` as a transitive dependency) | Environmental sensor |
| `SparkFun_LIS2DH12` | Accelerometer |
| `NeoPixelBus` | Status LED |
| `Adafruit_TinyUSB` (bundled with earlephilhower's RP2040 core, no separate install needed) | Dual-core USB serial console (CDC) |

This folder includes `platformio.ini` with all 4 `lib_deps` pinned and one
env per ISM region (`pico_tinyusb_us915` is the default; see
[Region configuration](#region-configuration) below). `pio run` from here
builds with no manual steps. If you use the Arduino IDE instead, install
the earlephilhower RP2040 core via Boards Manager and the libraries in the
table above via Library Manager before opening `firmware.ino`.

## Region configuration

The uplink and downlink center frequencies are picked at build time from
one of four ISM region presets. Every preset keeps a `+2 MHz`
uplink/downlink split (uplink is 2 MHz above downlink) except `EU433`,
which uses `+1 MHz` on half-MHz boundaries to fit a 250 kHz channel BW
strictly inside the CEPT ISM `433.05–434.79 MHz` window.

| Region (env)          | Uplink   | Downlink | Notes |
|---|---|---|---|
| `us915` (default)     | 918.0 MHz | 916.0 MHz | Historical hardcoded pair, `pio run` with no `-e` builds this. |
| `eu868`               | 869.0 MHz | 867.0 MHz | Both centers inside 863–870 MHz (CEPT). |
| `eu433`               | 434.5 MHz | 433.5 MHz | Both channels (±125 kHz) strictly inside CEPT ISM 433. |
| `as923`               | 924.0 MHz | 922.0 MHz | Japan/Korea/SG/NZ (AS923 plan). |

Build one specific env:

```shell
pio run -e pico_tinyusb_eu868          # firmware for Europe 868 MHz
pio run -e pico_tinyusb_eu433          # Europe/Asia 433 MHz ISM
pio run -e pico_tinyusb_as923          # Asia 923 MHz
```

To pin non-preset frequencies without adding an env, override the kHz
defines from `build_flags` (kHz gives sub-MHz precision):

```ini
build_flags = -DUSE_TINYUSB -DFLATSAT_UPLINK_FREQ_KHZ=915500 \
                            -DFLATSAT_DOWNLINK_FREQ_KHZ=913500
```

`regions.h` holds the preset table. When editing it, mirror the change in
`../Attacks/lib/regions.py` so the attack scripts stay tuned to what the
firmware is actually listening on.

## Pre-built binary

`build/flatsat-firmware.uf2` is a build of this exact source, generated
with the `platformio.ini` above (`pio run`, `pico_tinyusb_us915`
environment — the US915 region preset) — RAM 8.4% (22016/262144 bytes),
Flash 7.8% (163756/2093056 bytes). To flash:
hold the Pico's BOOTSEL button while plugging it in over USB (it enumerates
as a mass-storage volume), then copy the `.uf2` onto it — the Pico reboots
on its own into the new firmware. **Not verified on real hardware:** this
specific binary hasn't been flashed or tested on physical FlatSat hardware
— it's a clean recompile of the source to have a ready artifact, not
necessarily the exact binary that ran during development/testing. The
source code is identical either way; if you need the "ran on real
hardware" guarantee, flash and test this `.uf2` yourself before relying on
it for a live demo.

## New files (don't exist in the public firmware)

| File | What it does |
|---|---|
| `secure_link.cpp` / `.h` | Encrypts/decrypts the downlink payload with AES-128. A static 16-byte key embedded in the binary, ECB mode, no IV — the documented vulnerability. Exposes `secureLinkIsEnabled()`, `secureLinkEncodePayload()`, `secureLinkDecodePayload()`. |
| `spacecan.cpp` / `.h` | Simulated SpaceCAN bus console (serial port, text), with 3 nodes (`SENSOR`/`MOTOR`/`BATTERY`), fragmented-frame reassembly, frame injection with no origin check (`SC INJECT`), and manual node reset (`SC RESET`) — 3 intentional vulnerabilities documented in the file's own header. Also contains the PWNSAT console shell (banner, menu, sensor dashboard mode) — none of this touches the radio/USB command path. |

## Bugs fixed vs. the public firmware

1. **LoRa radios wouldn't initialize (-707 /
   `RADIOLIB_ERR_SPI_CMD_FAILED`) — root cause found and fixed.** The
   public firmware calls `radio0.begin()` / `radio1.begin()` with no
   arguments, which leaves `tcxoVoltage` at RadioLib's default (1.6V) —
   telling the chip to expect a TCXO this module doesn't have (it uses a
   plain XTAL), so internal calibration never completes. Fixed in
   `ruplink.cpp` / `rdownlink.cpp`: explicit `tcxoVoltage=0.0`.
2. **`downlinkRadioTransmit()` (blocking) could fail if a previous
   transmission hadn't finished.** Added `radio1.finishTransmit()` +
   `delay(100)` before transmitting.
3. **`uplinkRadioCheckPacketReceived()` corrupted the received payload in
   debug mode.** The public firmware does a hex-string → bytes → callback
   roundtrip that lost data; raw bytes (`byteArr`) are now passed straight
   to the callback instead.
4. **Misaligned Serial logs.** Several `Serial.printf(...)` calls in
   `ruplink.cpp`/`rdownlink.cpp`/`worker.cpp` ended in `\n` instead of
   `\r\n` — many serial terminals don't return to column 0 without the
   explicit `\r`. 32 occurrences fixed.

## New features

### Ground Station (GS) authentication and access control
A full subsystem in `worker.cpp`: GS modes (`GS_MODE`), access
challenge/response (`GS_ACCESS`), status (`GS_STATUS`). The access "gate"
requires the GPS to report a position within a 35km radius
(`gs_station_radius_m`) of a fixed GS coordinate
(`gs_station_lat_e7`/`gs_station_lon_e7`). The challenge/response uses a
hardcoded shared key (`gs_shared_auth_key = 0xC0DEFACE`) XORed against the
challenge — an intentional vulnerability, exploited by the `05_gs_auth_spoofing`
attack script.

### GPS navigation
`sensors.cpp`/`.h`: a full NMEA parser (GGA/RMC sentences), a new dedicated
UART (`PIN_GPS_TX`/`PIN_GPS_RX`, pins 0/1), a `gps_nav_t` struct with
fix/lat/lon/alt/satellite-count/UTC date-time. A new `GET_NAV` APID
(`0x0E`) exposes a navigation snapshot over telemetry.

### Mission modes
`SAFE` / `NOMINAL` / `PAYLOAD` / `SCIENCE` / `CONTINGENCY` (`mission.h`),
controllable via the new `SET_MISSION_MODE` APID (`0x0D`), with status
flags (`MISSION_FLAG_*`) reporting subsystem health (BME/ACC/GPS/secure
link/payload armed/USB debug active).

### Downlink encryption (secure link)
AES-128 active by default on the downlink payload (`secure_link.cpp`).
Toggled via the `AES_CONFIG` APID (`0x0A`). Static key, no rotation, no IV
— documented as a vulnerability, not an oversight.

### "Secured" SPP packet format (parallel, doesn't replace the existing one)
`spp.cpp`/`.h`: new `spp_tc_build_packet_secured()` /
`spp_tm_build_packet_secured()` functions that prepend a 4-byte secondary
header (a plain monotonic counter, **not cryptographic** — no IV, no
timestamp, no freshness validation) before the payload, setting the
`SecHdr` flag. Doesn't touch any of the 20+ existing callers of
`spp_build_packet()`.

### Other new APIDs
`FLASH_READ` (`0x0B`, reads up to 32 bytes from a fixed blob behind a
hardcoded "unlock tag" `0xC35A` — a flash-read vulnerability with no real
authentication), `GET_STATUS` (`0x0C`), `GET_PAYLOAD_STATUS` (`0x0F`),
`DEBUG_CONFIG` (`0x10`, enables debug commands over USB only).

### Command source separation (radio vs. USB)
The public firmware had a single `commandHandler()`. There are now
`commandHandlerRadio()` / `commandHandlerUSB()`, both reaching
`commandHandlerInternal(..., command_source_t source)` — this lets certain
commands (debug, some GS commands) be restricted to a specific origin
(`groundStationCommandAllowed()`, `source == COMMAND_SOURCE_USB` checks).

### Serial-console telemetry dashboard
`printSystemStatusDashboard()` / `telemetryDashboardWorker()` — an
interactive text mode that shows live sensor/GPS/GS/mission state,
launched from the PWNSAT console (`spacecan.cpp`), without affecting the
radio loop.
